This host follows a git repo.

Every reconcile beat (~1 min) it pulls the repo and copies shared/*.toml and hosts/<this-host>/*.toml into the deployments dir. Git owns the specs it brought: edit one on the host (here, or over ssh) and the next sync puts it back — change fleet-managed apps by committing to the repo. Deployments created on this page coexist; the fleet never touches files it didn't introduce.

Removing a spec from the repo retires the app on the next beat. Sync failures are fail-open: apps keep running on the last synced state.

The status line shows the last synced commit's age. Secrets never live in the repo — specs reference env files (.env/…) that exist only on the host, so the repo can be public.

docs: plybox.sh/docs/deployments/#gitops-fleet

{{end}} {{if eq .HelpTopic "host"}}

A deployment is a file.

/var/lib/ply/deployments/<name>.toml names a source (registry app, GitHub release, repo to build, or an image path) plus env, ports, domains. systemd watches the dir; any change runs ply reconcile, which makes reality match the files — creating, rolling, or removing apps. Deleting the file stops the app and removes its unit (volumes are kept).

update available means the source moved (a new release or commit). deploy now just touches the file — a touch is explicit intent, so it works even for auto = false apps. With the 1-minute timer, updates also flow with no clicks at all.

roll back pins a past version into the spec; the write itself triggers the (health-gated) roll. Edit the pin out to resume following latest. The expandable spec — view / edit is the whole truth: whatever you save there is what reconcile applies, and its verdict lands in the status line.

docs: plybox.sh/docs/deployments/

{{end}} {{if eq .HelpTopic "source"}}

Paste a repo, get a running app — no CI required.

Public repos are inspected: a GitHub release carrying a ply image recommends the pull CI image lane (the host downloads what your CI built); otherwise the build here lane clones and builds on this host in a fenced, throwaway builder. A package.json with next prefills a known-good preset; a ply.toml in the repo always wins.

Private repos: paste a fine-grained PAT with Contents: read on that one repo. The token is stored on this host (0600) and covers cloning, release downloads, and update checks — one credential for everything.

Pasting a fleet repo (it has hosts/<name>/ dirs) offers enrollment instead: this host starts following the repo.

docs: plybox.sh/docs/dashboard/

{{end}} {{if eq .HelpTopic "registry"}}

One-click services from the ply registry.

Each card is a published package — postgres, redis, community apps. Deploying writes a spec file naming the app; the image downloads pinned by hash, and the env textarea is prefilled with the service's contract (the variables it actually reads). internal:<port> publishes only to other apps on this host's bridge; a domain routes public traffic through the edge.

Filter as you type; the version dropdown pins, and leaving it on the newest keeps the app following releases.

docs: plybox.sh/docs/registries/

{{end}} {{if eq .HelpTopic "env"}}

References in specs, values on the host.

An env file lives at deployments/.env/<name>.env (0600) and specs point at it: env_file = ".env/<name>.env". Several apps can share one file — a stack's database password is written once. Because the spec carries only the path, fleet repos stay publishable.

save writes the file; save & apply also touches every spec that references it, so reconcile restarts those apps onto the new values. An app sees every key in the file it references — split files if you want tighter scopes.

Deleting a file that a spec still references is refused.

docs: plybox.sh/docs/deployments/#shared-env-files
